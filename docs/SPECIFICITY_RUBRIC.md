# A rubric for `task_specificity` — v2

**Status: ADOPTED by the owner 2026-09-21.** v2 is the live rubric.
`task_specificity` is computed from the five dimension scores stored in
each catalog entry; it is no longer a standalone number anyone can edit.

v1 and its scoring table are preserved below, marked superseded, for the
record. The owner's three edits to v1 changed **criteria only** and were
applied uniformly to all 26 benchmarks.

## What the rubric is trying to capture

The question is **not** "is this benchmark good?" or "is it hard?" — those
are discrimination and freshness, priced elsewhere. Specificity asks one
thing:

> If a model does well on this, how close is that to evidence it can do
> some **actual task somebody performs**?

A benchmark can be excellent and score low here. MMLU is a fine measure of
broad knowledge and a poor proxy for any particular job.

## The rubric

**Five** dimensions, each scored **0, 1 or 2**. Specificity = total ÷ 10,
reported to two decimals. Everything is decided from the benchmark's own
construction, so two people reading the same paper should land within one
point.

### A. Item provenance — where did the instances come from?

| | |
|---|---|
| **0** | Generated by a program or a model (synthetic, templated, procedurally constructed). |
| **1** | Written by humans specifically for the benchmark. |
| **2** | Taken from artifacts that already existed because someone was doing the real work — GitHub issues, real exams, production logs, user queries. |

### B. Output and check — does success here look like success outside the benchmark?

*(v2: merges v1's separate "response shape" and "grading" dimensions.)*

| | |
|---|---|
| **0** | Select from supplied options, or ranking/likelihood, or an unanchored model judge. |
| **1** | Short free-form answer matched against a stored reference. |
| **2** | The artifact the real task produces, verified by execution or a programmatic checker against a criterion that would count as success outside the benchmark. |

**Mixed cases** — e.g. a real artifact graded by reference match. Score
what the **output** would earn and what the **check** would earn
separately, and take the **LOWER**. Success only looks real if both are
real. A patch graded by string comparison is not a patch that worked; a
correct answer chosen from four options is not an answer produced.

### C. Scope — how many different things is it measuring?

| | |
|---|---|
| **0** | Deliberately spans many unrelated domains; a catch-all by design. |
| **1** | One broad domain (mathematics, science, code), a handful of related task types, **or a narrow task that exists only as an evaluation**. |
| **2** | One identifiable task type **that could be named in a job description**. |

*(v2 tightening: narrowness alone does not earn a 2. Pronoun
disambiguation measures exactly one thing and is still C1, because nobody
is employed to do it.)*

### D. Who does this? — is there a person whose work this resembles?

| | |
|---|---|
| **0** | Nobody performs this outside of evaluation. |
| **1** | A recognisable component of somebody's work, but not a deliverable on its own. |
| **2** | Substantially somebody's actual job output. |

**D1 or D2 requires that someone produces this output FORMAT in their
work.** Answering multiple-choice questions is **D0 regardless of subject
matter** — a physicist does physics, not four-option physics quizzes.

### E. Scale — is the unit of work the size of the real unit of work?

| | |
|---|---|
| **0** | Single step, or a few lines, resolved in one shot. |
| **1** | Multi-step, but within one context or file. |
| **2** | Spans files, turns, or tool calls the way the real task does. |

### Reading the result

| range | meaning |
|---|---|
| 0.80–1.00 | Doing well is close to direct evidence of doing the job. |
| 0.50–0.80 | A real task shape, but simplified, shortened, or narrowed. |
| 0.20–0.50 | A proxy: the skill is relevant, the activity is not real. |
| 0.00–0.20 | A measurement instrument with no real-world counterpart. |

## What this rubric deliberately does not do

- **It does not reward difficulty.** A trivially easy benchmark of a real
  task scores high. That is correct: difficulty is discrimination's job.
- **It does not reward quality.** A benchmark with a broken answer key
  scores the same as a clean one. Item quality is a separate penalty.
- **It does not reward popularity or adoption.**
- **It does not consider how the score is normally *used*.** A benchmark
  routinely over-read as a general capability measure is not penalised
  for that here.

## Known weaknesses of the rubric itself

Stated up front, because a rubric that hides its failure modes is worse
than no rubric.

1. **The min rule in B is a deliberate strictness choice, not a neutral
   one.** Taking the lower of output and check means a benchmark is
   credited only where *both* halves resemble real work. The alternative —
   averaging — would let a real artifact graded by string match score 1,
   and the rule rejects that on the grounds that a check which cannot
   recognise success is not evidence of success. It is a judgement, it
   biases scores downward, and it should be revisited if it ever produces
   a result that looks wrong. **Note: it currently binds on nothing** —
   no benchmark in the catalog has an output score different from its
   check score, so the rule is inert today and exists to constrain future
   entries.
2. **A ÷ 10 scale implies more precision than five coarse judgements
   support.** Two reviewers differing on two dimensions produce a 0.20
   gap. **Differences below ~0.2 should be treated as noise.** This is not
   decorative: see the sensitivity analysis in docs/BACKTEST.md, where
   single-point disagreements of exactly this size flip the backtest's
   verdict.
3. **E is the softest dimension.** "Multi-step" is a judgement, and the
   boundary between E0 and E1 is the least checkable line here.
4. **It has no notion of coverage or breadth-within-a-task.** A benchmark
   sampling one narrow corner of a real task scores identically to one
   covering it thoroughly.
5. **It cannot see contamination or leakage**, by design — but that means
   a benchmark whose real-world resemblance is precisely why it leaked
   (real GitHub issues are in the training data) is rewarded for the thing
   that broke it.
6. **Within-benchmark heterogeneity is averaged by hand.** BIG-Bench Hard
   is 23 tasks with different formats and graders; Humanity's Last Exam
   mixes multiple choice with short answer. Both are scored as one
   benchmark, which the rubric has no principled way to do.

## What adopting this does and does not establish

It makes every specificity value decomposable and checkable, and it
removes the possibility of a value being edited without a reason.

**It does not make specificity measured.** Five judgements are still five
judgements; the rubric moves the subjectivity from one number to five
smaller ones and makes it auditable. It must not be described as
measurement.

**It has not been independently checked.** Both the v1 values and the
rubric that replaced them were written by Claude Code. A second reviewer
scoring a sample against these criteria is the validation, and it has not
happened.

# A rubric for `task_specificity` — v1 (SUPERSEDED)

**Status: proposal. Nothing is applied.** The catalog is unchanged and no
score in this repo uses these numbers.

## Why this exists

`task_specificity` is 20% of every benchmark's trust score, nothing
measures it, and the field's own comment defines it as "your judgement of
how narrowly this maps to a real task". Three problems have accumulated:

1. Four of the 26 values were written by Claude Code rather than the
   owner, and are marked as unreviewed in the catalog.
2. The backtest's only error traces directly to one of those four. Moving
   MuSR from 0.30 to 0.34 — a change nobody could argue against — flips
   the test from 10/12 to 12/12.
3. There is no written standard, so no two values are guaranteed to mean
   the same thing, and nobody can check one.

A rubric does not fix (1) or (2). It fixes (3), which is what makes (1)
and (2) reviewable instead of arbitrary.

## Provenance of this document

Written 2026-09-21 by Claude Code, as a proposal for the owner to accept,
reject or amend. While drafting, the dimensions were sanity-checked
against five benchmarks (SWE-Bench Verified, MMLU, HumanEval, IFEval,
MuSR) to confirm they discriminate at all; those checks shaped the
rubric. **All 26 benchmarks were scored only after this document was
committed**, and no backtest was run with the resulting values — the
decision to adopt should be made on the rubric's merits, not on what it
does to a twelve-point test.

## How much would actually change

| | current | rubric |
|---|---:|---:|
| mean | 0.558 | 0.540 |
| median | 0.550 | 0.460 |
| standard deviation | 0.272 | 0.335 |

- Mean absolute change **0.092**. 18 of 26 move by ≤0.1; 22 of 26 by ≤0.2.
- Correlation with the current values: Pearson **+0.92**, Spearman **+0.91**.

**The honest reading of that is unflattering to the rubric, not
flattering.** It mostly reproduces the values it was written to replace.
It adds auditability — every number now decomposes into six checkable
judgements — but it does not discover that the existing values were
wrong. Anyone hoping this would settle the specificity problem should
note that a rubric agreeing with the guesses at ρ = 0.91 is evidence that
either the guesses were reasonable, or that the same person's intuitions
went into both. **Both were written by Claude Code, so the second cannot
be ruled out**, and that is the strongest argument for the owner scoring
a sample independently before adopting anything.

The rubric does spread the distribution (σ 0.27 → 0.34), pushing
multiple-choice benchmarks down and execution-graded ones up:

| grading style | n | mean Δ |
|---|---:|---:|
| executed / programmatic checker | 12 | **+0.066** |
| reference answer or fixed options | 14 | **−0.089** |

That is the B/C correlation weakness listed above, showing up exactly as
predicted. Whether it is a bias or the correct signal is the main thing to
decide: the rubric says a benchmark graded by running the result is closer
to real work than one graded by matching a stored string, and that claim
is doing a lot of work across 26 rows.

## The four divergences over 0.2

**GPQA Diamond: 0.60 → 0.17 (−0.43).** The largest disagreement in the
catalog and the one most worth arguing about. The current 0.60 rewards
the fact that PhD-level experts wrote the questions and that non-experts
with Google cannot answer them. The rubric refuses that: it is four-option
multiple choice, graded by picking a letter, with no artifact produced and
no one whose job this is. **The rubric is asserting that expert-authored
difficulty is not specificity — it is difficulty, which discrimination
already prices.** If that argument is wrong, the rubric is wrong, because
this follows directly from its design rather than from a marginal call.

**SimpleQA Verified: 0.60 → 0.33 (−0.27).** The catalog notes already
concede the point — "short-form parametric factuality is a real property
of a model but not a task a user performs" — and then record 0.60 anyway.
The rubric makes E0 count. This looks like the current value drifting
upward because the benchmark is *well built*, which is a different virtue.

**TruthfulQA: 0.40 → 0.17 (−0.23).** Scored here as the v1 leaderboard
runs it: multiple choice over supplied options, adversarially written to
elicit known misconceptions. Nobody performs this task. The current 0.40
appears to credit the *importance* of truthfulness rather than the task
shape.

**HumanEval: 0.45 → 0.67 (+0.22).** The only large upward move. The
rubric credits real code, executed tests, and one identifiable task type;
it can only dock HumanEval on F (164 single short functions) and on A
(hand-written for the benchmark). **This is where the rubric is most
likely to be wrong**, because HumanEval's problem is widely understood to
be triviality, and triviality is what F alone cannot carry. The rubric's
refusal to price difficulty is a deliberate choice, and HumanEval is the
case that makes it uncomfortable.

## Where the rubric was hard to apply

1. **Dimension E, on nearly every knowledge benchmark.** "Is answering
   graduate-level science questions a component of somebody's work?" is
   genuinely arguable — researchers know these things, they just don't
   answer multiple-choice questions about them. E0 was chosen
   consistently for MC knowledge tests, and that single call drives most
   of the downward moves. A reviewer who reads E1 into those instead
   would raise MMLU, GPQA, TruthfulQA and HLE by 0.08 each.
2. **Dimension D for single-task-type-but-not-a-job benchmarks.**
   Winogrande measures exactly one thing (pronoun disambiguation), which
   argues for D2, but "could be named in a job description" argues for
   D1. D1 was used throughout for this pattern — HellaSwag, Winogrande,
   MuSR, TruthfulQA — but the rule needs tightening before anyone else
   applies it.
3. **Dimension A when the task is constructed around real material.**
   MirrorCode asks models to reimplement real Unix utilities: the
   *program* is real, the *task* is invented. A2 was used because A asks
   about item provenance, but that reading makes A generous to any
   benchmark that points at something real.
4. **Dimension F for reasoning benchmarks.** GSM8K's 2–8 arithmetic steps
   and MuSR's 1,000-word narratives both got F1, which is unsatisfying —
   they are not comparable units of work. This is the softest dimension,
   as predicted.
5. **BIG-Bench Hard resists the rubric entirely.** It is 23 heterogeneous
   tasks with different formats and graders; scoring it as one benchmark
   averages across things the rubric wants to distinguish.

## What adopting this would and would not do

It would make every specificity value decomposable and checkable, replace
four unreviewed Claude Code judgements with four reviewable ones, and
force the difficulty-versus-task-shape distinction to be made explicitly
rather than absorbed silently.

It would not make specificity *measured*. Six judgements are still six
judgements; the rubric moves the subjectivity from one number to six
smaller ones and makes it auditable. It should not be described as
measurement in the README if adopted.

One fact the owner should have before deciding, stated because omitting
it would be the more manipulable choice: **the rubric moves MuSR from
0.30 to 0.17, i.e. downward, away from the 0.34 that would make the
backtest pass.** No backtest was run with these values and none should be
before the adoption decision — but nobody should be able to claim the
rubric was reverse-engineered to fix the test, and it plainly was not.
