# A rubric for `task_specificity`

**Status: proposal. Nothing is applied.** The catalog is unchanged and no
score in this repo uses these numbers.

## Why this exists

`task_specificity` is 20% of every benchmark's trust score, nothing
measures it, and the field's own comment defines it as "your judgement of
how narrowly this maps to a real task". Three problems have accumulated:

1. Four of the 26 values were written by Claude Code rather than the
   owner, and are marked as unreviewed in the catalog.
2. The backtest's only error traces directly to one of those four. Moving
   MuSR from 0.30 to 0.34 — a change nobody could argue against — flips
   the test from 10/12 to 12/12.
3. There is no written standard, so no two values are guaranteed to mean
   the same thing, and nobody can check one.

A rubric does not fix (1) or (2). It fixes (3), which is what makes (1)
and (2) reviewable instead of arbitrary.

## What the rubric is trying to capture

The question is **not** "is this benchmark good?" or "is it hard?" — those
are discrimination and freshness, priced elsewhere. Specificity asks one
thing:

> If a model does well on this, how close is that to evidence it can do
> some **actual task somebody performs**?

A benchmark can be excellent and score low here. MMLU is a fine measure of
broad knowledge and a poor proxy for any particular job.

## The rubric

Six dimensions, each scored **0, 1 or 2**. Specificity = total ÷ 12,
reported to two decimals. Everything is decided from the benchmark's own
construction, so two people reading the same paper should land within one
point.

### A. Item provenance — where did the instances come from?

| | |
|---|---|
| **0** | Generated by a program or a model (synthetic, templated, procedurally constructed). |
| **1** | Written by humans specifically for the benchmark. |
| **2** | Taken from artifacts that already existed because someone was doing the real work — GitHub issues, real exams, production logs, user queries. |

### B. Response shape — what does the model actually have to produce?

| | |
|---|---|
| **0** | Select one of N supplied options. |
| **1** | Short free-form answer: a number, a span, a name, a sentence. |
| **2** | The artifact the real task produces: a patch, a program, a command sequence, a document, a completed interaction. |

### C. Grading — does "correct" here mean correct out there?

| | |
|---|---|
| **0** | Ranking or likelihood over fixed options, or an unanchored model judge. |
| **1** | Exact or fuzzy match against a stored reference answer. |
| **2** | Executed or programmatically verified against a criterion that would count as success outside the benchmark: tests pass, a checker is satisfied, an environment reaches a target state. |

### D. Scope — how many different things is it measuring?

| | |
|---|---|
| **0** | Deliberately spans many unrelated domains; a catch-all by design. |
| **1** | One broad domain (mathematics, science, code) or a handful of related task types. |
| **2** | One identifiable task type that could be named in a job description. |

### E. Who does this? — is there a person whose work this resembles?

| | |
|---|---|
| **0** | Nobody performs this outside of evaluation. |
| **1** | A recognisable component of somebody's work, but not a deliverable on its own. |
| **2** | Substantially somebody's actual job output. |

### F. Scale — is the unit of work the size of the real unit of work?

| | |
|---|---|
| **0** | Single step, or a few lines, resolved in one shot. |
| **1** | Multi-step, but within one context or file. |
| **2** | Spans files, turns, or tool calls the way the real task does. |

### Reading the result

| range | meaning |
|---|---|
| 0.75–1.00 | Doing well is close to direct evidence of doing the job. |
| 0.50–0.75 | A real task shape, but simplified, shortened, or narrowed. |
| 0.25–0.50 | A proxy: the skill is relevant, the activity is not real. |
| 0.00–0.25 | A measurement instrument with no real-world counterpart. |

## What this rubric deliberately does not do

- **It does not reward difficulty.** A trivially easy benchmark of a real
  task scores high. That is correct: difficulty is discrimination's job.
- **It does not reward quality.** A benchmark with a broken answer key
  scores the same as a clean one. Item quality is a separate penalty.
- **It does not reward popularity or adoption.**
- **It does not consider how the score is normally *used*.** A benchmark
  routinely over-read as a general capability measure is not penalised
  for that here.

## Known weaknesses of the rubric itself

Stated up front, because a rubric that hides its failure modes is worse
than no rubric.

1. **B and C are correlated.** Benchmarks producing real artifacts tend to
   be verified by execution, so those two dimensions often move together,
   effectively double-weighting "executable" and pushing all code
   benchmarks up as a class.
2. **F is the softest dimension.** "Multi-step" is a judgement, and the
   boundary between F0 and F1 is the least checkable line here.
3. **A ÷ 12 scale implies more precision than six coarse judgements
   support.** Two reviewers differing on two dimensions produce a 0.17
   gap. Differences below ~0.2 should be treated as noise.
4. **It has no notion of coverage or breadth-within-a-task.** A benchmark
   sampling one narrow corner of a real task scores identically to one
   covering it thoroughly.
5. **It cannot see contamination or leakage**, by design — but that means
   a benchmark whose real-world resemblance is precisely why it leaked
   (real GitHub issues are in the training data) is rewarded for the thing
   that broke it.

## Provenance of this document

Written 2026-09-21 by Claude Code, as a proposal for the owner to accept,
reject or amend. While drafting, the dimensions were sanity-checked
against five benchmarks (SWE-Bench Verified, MMLU, HumanEval, IFEval,
MuSR) to confirm they discriminate at all; those checks shaped the
rubric. **All 26 benchmarks were scored only after this document was
committed**, and no backtest was run with the resulting values — the
decision to adopt should be made on the rubric's merits, not on what it
does to a twelve-point test.
